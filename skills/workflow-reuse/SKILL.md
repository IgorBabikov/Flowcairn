# Reuse decision

- Inspect current manifests, versions, architecture and equivalent local components first. Preserve the project's stack and conventions. Do not replace a working component merely because another library is popular.
- Recommend a ready-made component only for a concrete missing capability. Verify its published documentation, full relevant instructions, dependencies, compatibility and license before import. Unresolved provenance or license remains unresolved.
- Distinguish a Skill (guidance), tool (authorized execution), library (code dependency) and verifier (evidence). Loading instructions does not install a CLI, authorize a command or prove the result.
- Use the pinned project Skills and registered checks selected by the trusted runtime. Suggest missing capabilities explicitly; do not create executable registrations, invoke forbidden MCP/tools or update floating instructions inside an authorized plan.
- Select only methods needed by the current phase, scope, framework/version, task and risk. For a routine change, avoid optional design exploration, scans or process artifacts while preserving the mandatory checks and rights.
