# Участие в Flowcairn

Начните с [устройства системы](docs/HOW-FLOWCAIRN-WORKS.md), [архитектуры](docs/ARCHITECTURE.md) и [ограничений](docs/LIMITATIONS.md). Изменение должно решать конкретную проблему пользователя и сохранять прослеживаемость Requirement → Work → Evidence → Conclusion. Уязвимости обсуждаются [приватно](SECURITY.md).

## Разработка и проверки

Нужен Node.js 22. Базовые команды:

```bash
npm ci --ignore-scripts
npm run build
npm run typecheck
npm run lint
npm test
```

Для UI дополнительно выполните `npm run test:ui`. Изменения экспортируемых файлов проверьте через `npm run check:public` и `npm run check:package`. Условия отдельных проверок описаны в [VERIFICATION](docs/VERIFICATION.md); недоступный Docker, браузер или AI-провайдер не считается успешной проверкой. Реальные платные AI-вызовы не должны запускаться незаметно.

Собранный интерфейс хранится в Git для установки без lifecycle scripts. После правки UI включите обновленный `tools/ai-graph-viewer/dist` в тот же diff; CI проверяет соответствие сборки исходникам.

## Локальный пакет

Для проверки текущих исходников до публикации выполните в репозитории Flowcairn:

```bash
npm ci --ignore-scripts
npm run build
npm pack --ignore-scripts
```

Затем установите созданный архив в отдельный тестовый проект:

```bash
npm install --ignore-scripts -D /path/to/package.tgz
```

Подставьте путь к архиву, созданному `npm pack`. Команда запуска указана в поле `bin` его `package.json`. Наличие архива не означает публикацию в npm.

## Архитектура и доказательства

Executor владеет состоянием, permissions и допустимыми переходами. UI отображает snapshot/capabilities. Сохраняйте runtimeRoot/projectRoot, immutable hashes, CAS, idempotency, ограниченный контекст и доказательства остановки процесса.

Меняйте конкретную ответственность. Если модуль перегружен, выделите связанную область с узким API и сохраните проверяемое поведение; не добавляйте еще одну параллельную систему и не делите файлы только ради числа строк.

Успех node или общий review pass не означает PROVEN. Изменения proof engine должны проверять полное покрытие, связь evidence с требованием и актуальным результатом, отсутствие подходящего verifier, failed verification, bounded repair/reverification и recovery. Нельзя ослаблять критерий или validator ради зеленого теста. Проверки UI должны подтверждать, что он не показывает доказанность вопреки runtime.

## Pull request

Опишите проблему, наблюдаемый результат, выполненные проверки и ограничения. Для нового verifier покажите, что именно он доказывает; для permissions/state/recovery добавьте значимые отрицательные сценарии. Для UI приложите безопасное визуальное подтверждение. Новая платформа требует реальной проверки, а не только измененной документации.

Поддерживайте документацию согласованной с реализацией. Не включайте секреты, личные пути, закрытый код, session URL или историю внутренних запусков. Не заявляйте качество, стоимость или ускорение без данных. Перед merge нужны независимый review конкретного diff и подходящие успешные проверки.
