# Конфигурация проекта

`.flowcairn.json` задает AI-клиент, разрешенный контекст, проектные проверки и выбранные Skills. Ключи, пароли и содержимое сессий в профиль не помещаются. Текущая schema определяется [project.mjs](../scripts/ai-graph/lib/project.mjs).

## Настройка и согласия

`npx flowcairn init` создает профиль и локальную установку. Повторный `init` сохраняет профиль: переданный повторно `--model` не заменяет его настройки. Для перенастройки остановите Flowcairn и выполните `npx flowcairn setup`.

`setup` меняет AI-настройки, подход к тестам и выбранные проверки. Для существующих npm scripts сохраняется прежний путь настройки. `setup --check-profile checks.json` явно регистрирует [команды любого стека](CHECK-PROFILES.md). Новые планы связывают определения команд, объявленные входы и инструменты с хешами; изменение привязки не разрешает новую команду старому плану. Переход в `none` выключает проверки и снимает прежнюю привязку.

`setup --outputs` заменяет полный список `outputPaths`. Передайте все нужные каталоги через запятую, включая ранее настроенные. В универсальном профиле список должен включать outputs всех зарегистрированных проверок. Определяйте их по конфигурации сборщика; каталоги исходников исключать нельзя. Обычные `coverage`, `dist` и другие стандартные outputs исключаются общей политикой. После смены outputs старые снимки могут устареть; остановленный анализ без изменений можно продолжить после явного подтверждения свежего контекста. История прежней попытки сохраняется.

Профиль можно хранить в Git. Локальное согласие на чтение связано с полным профилем и каноническим корнем проекта в исключенной из Git записи установки. Одного `readConsent: true` в JSON недостаточно; clone и смена настроек не переносят согласие незаметно.

Изменение scope, инструкций, Skills, AI-конфигурации или проверок может сделать текущий план неактуальным. Не исправляйте сохраненные hashes вручную. Новое исполнение должно использовать актуальный план и разрешения.

## Поля профиля

| Поле | Назначение |
| --- | --- |
| `version` | `1` — существующий адаптер npm scripts; `2` — универсальный профиль команд. Это не версия API или плана задачи |
| `workspaceMode` | `direct` — файлы текущего проекта (по умолчанию); `worktree` — отдельная Git-копия по явному выбору только для профиля npm scripts (`version: 1`). Универсальный профиль (`version: 2`) поддерживает только `direct` |
| `integrationBranch` | Обязательное поле профиля; используется для интеграции в `worktree`. В `direct` установщик записывает текущую Git-ветку либо `direct` для проекта без Git |
| `packageManager` | Для профиля `1`: `npm`, `pnpm` или `yarn`, согласованный с manifests и lockfile |
| `contextPaths` | Дополнительные разрешенные пути чтения |
| `checks` | Идентификаторы зарегистрированных обязательных проверок; у профиля `1`: `typecheck`, `lint`, `tests`, `build` |
| `checkMode` | `none`, `hardened` или `trusted-local` |
| `checkScripts` | Для профиля `1`: сопоставление проверок с существующими scripts проекта |
| `checkProfile` | Для профиля `2`: определения executable/argv/cwd, входов, результатов, времени и ограниченного окружения команд |
| `outputPaths` | Результаты инструментов, исключаемые из исходников; не `src` и не весь репозиторий |
| `manifests` | Root и workspace manifests, lockfile, необходимые конфигурации менеджера |
| `skillManifest` | До четырех project Skills: путь, hash, этапы и область |
| `onboarding.testPolicy` | `keep` — сохранить подход проекта; `add` — добавлять тесты по задаче |
| `onboarding.coverage` | Явный выбор измерения покрытия; процент не назначается автоматически |
| `onboarding.readScope` | `project-files` для прямой работы в проекте; `tracked-project` для Git-режима |
| `ai.provider` | `codex`, `claude` или `cursor` |
| `ai.modelMode` | `provider`, `manual` или `auto` |
| `ai.model`, `ai.reviewModel` | Основная и, при явной настройке, отдельная модель ревью |
| `ai.reasoningEffort`, `ai.reviewReasoningEffort` | Настройки усиления для Codex |
| `ai.codexPath` | Необязательный путь к проверяемому Codex CLI |
| `ai.providerPath`, `ai.providerVersion` | Сохраненные путь и точная версия Claude Code/Cursor |
| `ai.providerManaged` | CLI поставляется и обновляется managed runtime Flowcairn; версия меняется только после capability-проверки |

## Модель и строгость

Для Codex доступны три режима:

- `provider`: безопасно прочитать только `model` и `model_reasoning_effort` из конфигурации CLI и передать их явно. Если их нет, Codex использует собственные настройки по умолчанию. Остальные настройки CLI и выбор активного IDE-чата не наследуются.
- `manual`: одна явно заданная модель и усиление для всех этапов.
- `auto`: явно заданные основная и review-модель; усиление в планах с контрактом зависит от rigor: `high` для высокого риска, `low` для легкой задачи вне review, иначе `medium`. Это не автоматический поиск моделей аккаунта.

Claude Code и Cursor используют режим `provider` с `provider-default`; модель определяет настроенный клиент. Flowcairn не подменяет недоступную модель. Другая модель для review сама по себе не доказывает независимость или качество.

## Проектные проверки

| Проверка | Conventional script |
| --- | --- |
| `typecheck` | `typecheck`, иначе `compile` |
| `lint` | `lint` |
| `tests` | `test` |
| `build` | `build` |

`trusted-local` — default нового локального проекта: он запускает зарегистрированные команды с правами пользователя. `none` не запускает проверки; новый план без обязательного verifier не получает разрешение на исполнение. `hardened` сохранен как совместимое имя того же локального режима, Docker не требуется. Служебные npm-логи и кеш направляются в приватное хранилище Flowcairn. Произвольные executable/argv из описания задачи или ответа AI не принимаются.

Наличие configured check не доказывает требование. Метод `check` дополнительно связывает фактически выполненную проверку с конкретным критерием; [подробнее о evidence](HOW-FLOWCAIRN-WORKS.md).

## Контекст, scope и manifests

`scope` задачи разрешает изменения, `contextPaths` разрешает дополнительное чтение, `forbiddenPaths` запрещает доступ к выбранным путям. `outputPaths` обозначает generated outputs и не дает право скрыть исходники или секреты от проверки.

Адаптер npm scripts обнаруживает root `package.json`, lockfile и workspace manifests. Для pnpm поле `packages` из `pnpm-workspace.yaml` имеет приоритет над `package.json.workspaces`; для npm учитываются массив `workspaces` и объект `workspaces.packages`. Универсальный профиль использует явно выбранные команды и их входы; наличие npm-файлов доставки Flowcairn не выбирает за него стек.

Пути workspace должны быть относительными и находиться внутри проекта. Если проект использует Git, игнорируемый workspace manifest вызывает `WORKSPACES_IGNORED`; уточните workspace-конфигурацию или правила игнорирования. Не скрывайте проблему удалением обязательного manifest.

`--manifests` при `init` задает полный список через запятую, а не дополнение к обнаруженному. Повторный `init` не пересобирает список уже существующего профиля. Изменение структуры проекта требует проверки manifests и нового окружения проверок.
