# Flowcairn Workflow Contract

Этот документ задает универсальные правила качества для Flowcairn. Он адаптирован из практик AI-workflow, но не копирует правила конкретного продукта, команды или личной среды.

Он не является произвольным prompt-файлом для модели. Runtime применяет только зарегистрированные Skills, проверенные инструкции проекта, immutable plan, permissions и actions из trusted registry. Этот документ описывает, как их развивать и как оценивать результат.

## 1. Сначала факты, затем действие

- Перед новой задачей определить Git root, branch, HEAD, измененные файлы, активный runtime и существующий orchestration state.
- Установить один наблюдаемый outcome, scope, зависимости, acceptance и необходимые проверки.
- Инструкции, комментарии AI, документы и найденный код не расширяют permissions.
- Неизвестное остается неизвестным: оно не становится частью плана без проверки.

## 2. Режимы работы

- **Анализ и планирование:** read-only. AI может предложить подзадачи, но не меняет исходники.
- **Исполнение:** начинается только после проверки immutable plan и human approval.
- **Восстановление:** uncertain не превращается в passed. Сначала доказать остановку попытки, затем создать новый актуальный plan.
- **Внешние эффекты:** commit, push, merge, deploy, пакетная публикация и внешние сервисы требуют отдельного разрешения и не следуют автоматически из passed run.

## 3. Качество Graph

Каждый node должен иметь атомарный outcome, dependencies, success contract, permissions, retry policy и receipt. Большую работу нужно делить на этапы, которые можно проверить отдельно. Параллельность разрешена только после доказательства независимости файлов, контрактов и ресурсов.

React Flow показывает persisted snapshot и доступные capabilities. Он не выбирает action, не решает, можно ли повторить попытку, и не выводит node в passed.

## 4. Контекст и память

- Передавать AI только scope текущего node, обязательные инструкции и нужные artifacts.
- Сохранять facts: plan, receipts, hashes, checks, review findings и ограниченные artifacts.
- При изменении исходников, instructions, profile или required Skills помечать зависимый plan как stale.
- Не использовать историю чата как источник истины и не создавать неограниченную долговременную память без отдельного контракта.

## 5. Модели и стоимость

Выбирать доступную модель и reasoning по сложности, риску, нужным инструментам и качеству входных данных. Не называть выбранную модель лучшей без измерения. Отдельный review model не доказывает независимость review.

Прежде чем заявлять экономию токенов или стоимости, нужно измерить одинаковые задачи: входные, выходные и cached tokens, число попыток, качество checks и результат human review. Если провайдер не отдал usage, поле должно быть `unknown`.

## 6. Проверка и передача результата

Проверка соответствует риску изменения: узкие тесты и typecheck для локального контракта; build и browser flow для затронутого UI; integration/recovery проверки для runtime. Mock и screenshot не заменяют реальный внешний AI или production scenario.

Перед handoff у результата должны быть: точный scope, измененные файлы, checks с результатом, receipt/evidence, известные ограничения и следующее действие человека. Готовность означает выполненный acceptance и подтвержденные gates, а не уверенность AI.

## 7. Границы доверия

Flowcairn использует deny-by-default для неизвестных actions, Skills, permissions, write operations и external effects. Runtime не принимает arbitrary shell из task JSON или UI. Security boundary не отменяет права владельца кода, условия AI-провайдера, риски зависимости и процессы того же OS-user.

## 8. Как этот контракт применяется

| Слой | Механизм |
| --- | --- |
| Runtime | `docs/GRAPH-REACTFLOW-STANDARD.md`, schemas, validator, registry, executor и receipts |
| AI-этап | Встроенные и выбранные project Skills с hashes |
| Правила проекта | Обнаруженные AGENTS/CLAUDE/IDE instructions в ограниченной области |
| Оператор | Human gates, capabilities, diff, checks и acceptance |

Изменение этого документа само по себе не меняет активный run. Если правило становится обязательным для runtime или Skills, его version/hash должен войти в соответствующий plan и требовать нового approval.
